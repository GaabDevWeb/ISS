Dicionário de Dados

O Dicionário de Dados é um artefato na Engenharia de Software para documentar, de
maneira estruturada e padronizada, todos os dados relevantes do sistem. Descreve com
precisão o significado, a estrutura e as restrições associadas a cada elemento.
Serve como fonte de verdade semântica do sistema.
Permite que o diagrama de classes permaneça limpo e legível.
A construção de um Dicionário de Dados precisa equilibrar dois objetivos:
1. Precisão técnica
2. Legibilidade


                                                                                       2
Dicionário de Dados
- Precisão técnica
O dicionário deve ser suficientemente rigoroso para permitir que analistas,
desenvolvedores e arquitetos de software compreendam exatamente:
- Quais dados existem no sistema
- Quais formatos são permitidos
- Quais valores são válidos ou inválidos
- Quais restrições e regras se aplicam a cada elemento
para evitar interpretações divergentes durante a implementação, os testes e a
manutenção do sistema.

                                                                                3
Dicionário de Dados

- Legibilidade
O Dicionário de Dados deve ser compreensível para usuários do negócio e demais
stakeholders não técnicos. Utiliza:
- Definições claras e objetivas
- Linguagem acessível: Termos alinhados ao vocabulário do domínio do problema.
O modelo de dados tem que ser discutido, validado e refinado de forma colaborativa,
reduzindo riscos de desalinhamento entre a área técnica e o negócio.

Dicionário de Dados

Notação
Concatenação +: indica a composição de elementos;
Repetição { }: indica que um elemento pode ocorrer várias vezes;
Opcionalidade ( ): indica que um elemento é opcional;
Seleção alternativa [ | ]: indica escolhas possíveis entre alternativas;
Comentários em itálico: esclarecem o significado dos elementos.

Diagrama de Classes


O Diagrama de Classes representa a estrutura estática do sistema, identificando:
- as principais classes (abstrações do domínio)
- Seus atributos (dados que cada classe armazena)
- Seus métodos (comportamentos associados)
As relações entre classes, como associações, heranças e dependências.




                                                                                   14
Diagrama de Classes


O diagrama fornece uma visão de alto nível da arquitetura do sistema, servindo como base
tanto para a implementação quanto para a comunicação entre os membros da equipe.
O diagrama de classes não deve ser construído isoladamente. Ele evolui em conjunto com
outros modelos, como Casos de uso, Diagramas de interação, Regras de negócio, etc. À
medida que o sistema evolui, novos detalhes, como restrições adicionais, formatos de
dados e regras específicas, podem ser incorporados ao Dicionário de Dados sem
comprometer a clareza visual do diagrama de classes.

Diagrama de Classes
A UML fornece uma notação padronizada para representar classes, seus atributos, seus
comportamentos e os relacionamentos entre elas. A notação UML não cria o modelo
sozinha. Ela expressa graficamente um entendimento que precisa ser construído por um
processo de análise iterativo.
Representação de uma classe
Uma classe é representada como um retângulo dividido em compartimentos:
- Nome da classe (obrigatório)
- Atributos (opcional na análise inicial)
- Operações/Métodos (responsabilidades)

Diagrama de Classes
Como evitar classes erradas?
1) Não confundir atributo com classe
Ex: valor da diária não deve virar classe. É atributo de Bicicleta.
2) Evitar redundâncias
número de dias, duração estimada, tempo do aluguel podem ser a mesma ideia
representada por termos diferentes.
3) recibo não é classe do domínio. É um documento derivado dos dados existentes.
4) Aluguel é a relação entre Cliente e Bicicleta, mas contém dados próprios (data, diárias,
multa, recibo) -> Precisa ser tratado como entidade.

Diagrama de Classes
Exercício 1
Considere um sistema de informação para uma loja de aluguel de bicicletas. Os requisitos
incluem:
Um cliente pode alugar uma ou mais bicicletas.
Cada bicicleta pode ser alugada várias vezes ao longo do tempo.
Para cada aluguel, devem ser registrados: data de início, número de diárias, valor pago
antecipadamente, possíveis descontos no depósito (atraso ou dano)
O sistema deve manter o histórico de aluguéis. Onde armazenar as informações do
aluguel?

                                                                                           21
Diagrama de Classes

Tentaiva 1. Armazenar os dados do aluguel diretamente na classe Cliente.
Cliente. nome, cpf, endereco, dataInicio, numeroDeDiarias
Se o cliente pode ter vários aluguéis, então:
- Um único atributo dataInicio não é suficiente.
- Um único atributo numeroDeDiarias não é suficiente
Não existe correspondência clara entre datas e bicicletas alugadas
-> O aluguel não é um simples atributo do cliente.


                                                                           22
Diagrama de Classes

Tentativa 2. Armazenar os dados do aluguel diretamente na classe Bicicleta.
Se a bicicleta pode ser alugada repetidamente:
Um único dataInicio não é suficiente.
Um único numeroDeDiarias não é suficiente.
Solução forçada: uso de listas.
-> O aluguel não é um simples atributo da bicicleta.



                                                                              23
Diagrama de Classes

Solução:
Os dados do aluguel descrevem algo que acontece entre cliente e bicicleta. Tem dados
próprios e precisa ser registrada historicamente.
Cada instância da classe Aluguel representa:
- um cliente específico
- uma bicicleta específica
- um período específico
- um conjunto específico de valores financeiros

Diagrama de Classes



O pagamento é independente, com dados próprios, histórico próprio e responsabilidades
